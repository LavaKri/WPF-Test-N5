# Constats — Menus : items désactivés et raccourcis

Constats d'essai (UIA, lecteur d'écran) repris de `Docs/Notes.md`, section 5, sans changement de contenu. Retour à l'index : [`Notes.md`](../Notes.md).

## Items de menu désactivés : sautés au clavier, donc invisibles pour NVDA

Constat de l'utilisateur (NVDA, .NET Framework 4.8, 2026-11-17) : « Choix d'un dossier... », désactivé en 4.8, « n'est pas là » dans le menu Fichier. Recherches du 2026-11-17 :

- **WPF** (code source, `MenuItem.cs`) : `IsEnabledCore` vaut `base.IsEnabledCore && CanExecute`. Un item à `IsEnabled="False"`, ou dont la commande ne peut pas s'exécuter, est grisé **et** non focalisable ; la navigation aux flèches (`KeyboardNavigation`) le saute. NVDA ne s'y arrête donc jamais. L'item reste dans l'arbre UIA (`IsEnabled` faux) : la navigation par objets de NVDA devrait le trouver (à vérifier).
- **Win32** : les menus natifs laissent arriver le focus sur un item grisé, et les lecteurs d'écran l'annoncent « indisponible » (« Annuler, indisponible ») ; c'est le cas du Bloc-notes. Windows n'est pourtant pas cohérent : Edge saute ces items, comme macOS et Linux ([Mozilla, bug 1702629](https://bugzilla.mozilla.org/show_bug.cgi?id=1702629)).
- **WinForms** : Microsoft a corrigé exactement ce défaut en .NET Framework 4.7.1 : « Narrator can now read disabled ToolStripMenuItem text, whereas previously it would skip over disabled menu items » ; et en 4.7.2, Narrateur « indicates when a ToolStripMenuItem has its Enabled property set to false » ([What's new in accessibility in .NET Framework](https://learn.microsoft.com/en-us/dotnet/framework/whats-new/whats-new-in-accessibility)). Aucune correction équivalente pour WPF dans cette page, ni d'issue trouvée dans dotnet/wpf.
- **W3C, ARIA Authoring Practices** ([Keyboard Interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface), focusabilité des contrôles désactivés) : dans les widgets composés, les éléments désactivés doivent **rester focalisables** (`aria-disabled`), entre autres « Menu items in a Menu or menu bar », les boutons Couper / Copier / Coller d'une barre d'outils, les options d'une liste, les onglets et les nœuds d'arbre. Les conventions ARIA reprennent celles des interfaces de bureau (Windows, macOS, GNOME).
- **Guide de conception de Windows** : désactiver un item qui ne s'applique pas au contexte plutôt que le retirer, pour que l'utilisateur sache que la commande existe (voir aussi Raymond Chen, [When do you disable an option and when do you remove it?](https://devblogs.microsoft.com/oldnewthing/20040514-00/?p=39343)). Avec WPF, un item désactivé est pour un utilisateur de NVDA aussi introuvable qu'un item retiré.
- Moyens possibles dans WPF (rien de natif) :
  1. **Item dérivé de `MenuItem`** : il reste activé pour WPF (focalisable), il est affiché en gris (couleur système du texte désactivé), son peer UIA déclare `IsEnabled` faux (NVDA dit « indisponible », l'`Invoke` UIA est refusé), et le clic, Entrée et le raccourci sont sans effet. C'est la méthode qui reproduit le comportement Win32 ; c'est la même technique que les peers dérivés recommandés par Microsoft pour corriger l'accessibilité WPF (Guy Barker). Écart à la règle « contrôles standard ».
  2. **Item laissé activé, grisé par un style, avec `AutomationProperties.ItemStatus` « indisponible »** : sans classe dérivée, mais l'UIA déclare l'item activé (faux pour tout client UIA), et la lecture d'`ItemStatus` par NVDA n'est pas vérifiée.
  3. **Retirer l'item** (`Visibility="Collapsed"`) : contraire au guide de Windows.
  4. **Laisser le natif** : l'utilisateur peut chercher l'item par la navigation par objets ; peu praticable.
- **Confirmé par l'utilisateur** (NVDA, .NET 10 et .NET Framework 4.8, 2026-11-17) : correctif coché, les items grisés sont atteints par les flèches et ne s'activent pas ; décoché, ils redeviennent introuvables.
- Choix de l'utilisateur (2026-11-17) : méthode 1, `Correctifs/CorrectifMenuIndisponible.cs` (classe `ItemMenuAtteignable`), item *Correctif > Atteindre les items indisponibles*, et item de vérification *Fichier > Toujours grisée* (`Specs/Fenetre.md`, 2.1, et `Specs/Correctifs.md`).

### Variante par patch Harmony (étude du 2026-11-17, non codée)

But : garder `IsEnabled="False"` et les commandes comme d'habitude, sans classe dérivée, pour tous les `MenuItem`.

- Code de WPF lu : `UIElement.IsEnabled` est calculé par `CoerceIsEnabled` (privée, statique) à partir de la valeur posée, de l'état du parent et de `IsEnabledCore` (`CanExecute` pour `MenuItem`). Le refus du focus est ailleurs : `Keyboard.IsFocusable` (PresentationCore, interne, statique) rend faux si `IsEnabled` est faux, et `KeyboardDevice` réévalue le focus (et le retire) quand l'élément focalisé devient désactivé ; `KeyboardNavigation.IsFocusableInternal` (PresentationFramework, interne, statique) refait le même test pour la navigation (Tab, flèches, `ItemsControl`).
- Variante A, patcher `CoerceIsEnabled` (l'item reste activé pour WPF) : simple, mais `IsEnabled` répond vrai pour un item désactivé (le code de l'application lit une valeur fausse), et il faut griser et déclarer l'indisponibilité soi-même.
- Variante B, patcher seulement le **refus du focus** pour les `MenuItem` : `Keyboard.IsFocusable` et `KeyboardNavigation.IsFocusableInternal` rendent vrai pour un `MenuItem` désactivé (visible et focalisable par ailleurs), et `MenuItem.OnClick` est ignoré tant que l'item est désactivé. `IsEnabled` reste **vrai** à lire (faux pour un item désactivé) ; le grisé (modèle du thème), l'état UIA « indisponible » et le refus d'`Invoke` restent ceux de WPF. Risque : d'autres chemins de WPF supposent peut-être qu'un élément focalisé est activé (à tester).
- **Choix de l'utilisateur (2026-11-17) : variante B**, `Correctifs/CorrectifMenuIndisponible.cs` réécrit (la classe `ItemMenuAtteignable` est retirée) ; quatre patches : postfix de `Keyboard.IsFocusable`, `KeyboardNavigation.IsFocusableInternal` et `KeyboardNavigation.IsTabStop` (ce dernier trouvé à la lecture : la navigation aux flèches, `PredictFocusedElement`, teste `IsElementEligible` puis `IsTabStop`), préfixe de `MenuItem.ClickItem(bool)`. Vérifié hors application (programme console temporaire) : les quatre patches s'appliquent, se retirent et se réappliquent en .NET 10.0.15 et en .NET Framework 4.8.10008.0.
- Présence des méthodes vérifiée par leur nom dans les assemblys installés : `IsFocusableInternal` (PresentationFramework) et `IsFocusable` (PresentationCore), en .NET Framework 4.8 et en .NET 10.

## Raccourci d'un item de menu (« Ctrl+O ») jamais annoncé

Constat de l'utilisateur (NVDA, .NET 10 et 4.8, 2026-11-17) : *Fichier > Ouvrir* n'est jamais annoncé avec « Ctrl+O », bien que le raccourci soit affiché dans l'item.

- Code de WPF (`MenuItemAutomationPeer.cs`) : le peer d'un `MenuItem` redéfinit la touche d'accès (`GetAccessKeyCore`, préfixée de « Alt+ » au premier niveau) et le nom, mais **pas** `GetAcceleratorKeyCore` : la propriété UIA `AcceleratorKey` reste vide (celle d'`AutomationProperties.AcceleratorKey`, non posée). Le texte du raccourci (`InputGestureText`, tiré de la commande) n'est qu'affiché.
- Code de NVDA (`NVDAObjects/UIA/__init__.py`, `_get_keyboardShortcut`) : NVDA lit `AccessKey` **et** `AcceleratorKey` et les annonce à la suite. Il annoncerait donc « Ctrl+O » si WPF le fournissait.
- Comparaison : un menu Win32 met le raccourci dans le texte de l'item (lu avec le nom) ; Microsoft a ajouté l'annonce du raccourci des `ToolStripMenuItem` de WinForms en .NET Framework 4.7.2.
- Recherches du 2026-11-17 :
  - **Microsoft, WinForms** ([Accessibility Insights, MenuItem AcceleratorKey](https://learn.microsoft.com/en-us/accessibility-tools-docs/items/winforms/menuitem_acceleratorkey)) : même défaut décrit (« the screen reader does not announce details of the accelerator keys ») ; corrigé par Microsoft dans WinForms à partir de .NET Framework 4.7.2, où le raccourci est exposé dans la propriété UIA `AcceleratorKey` (« Ctrl+N »). C'est la propriété que les lecteurs d'écran attendent.
  - **WPF** : aucune correction ; d'après un membre de l'équipe WPF cité dans [QuickMail, issue 849](https://github.com/kellylford/QuickMail/issues/849), exposer le raccourci est « le travail de l'application ». Même constat de code : `MenuItemAutomationPeer` n'a pas de `GetAcceleratorKeyCore`.
  - **Mesures du même projet** (WPF) : NVDA, « Annoncer les raccourcis clavier des objets » activé : item avec seulement `InputGestureText` : « Reply R 1 of 12 » (raccourci jamais dit) ; avec `AcceleratorKey` posé : « Manage Rules R Ctrl+Shift+L 2 of 4 ». Bouton avec une infobulle qui contient déjà le raccourci **et** `AcceleratorKey` : annonce en double (« New Message button New Message (Ctrl+N) Ctrl+N »). Narrateur, verbosité par défaut : ni l'un ni l'autre. JAWS : lu. Solution retenue par ce projet : `AutomationProperties.AcceleratorKey` posé sur les items et les boutons, alimenté par le raccourci réel de la commande.
- Moyens possibles dans WPF :
  1. **`AutomationProperties.AcceleratorKey` lié à `InputGestureText`** (`{Binding InputGestureText, RelativeSource={RelativeSource Self}}`) sur chaque item : sans classe dérivée ; le texte reste celui qui est affiché (raccourci de la commande, ou `InputGestureText` posé à la main).
  2. Le même lien posé **pour tous les `MenuItem` à la fois** par un gestionnaire de classe (`EventManager.RegisterClassHandler(typeof(MenuItem), LoadedEvent, …)`), seulement si l'application n'a pas posé `AcceleratorKey` elle-même : un seul appel, couvre les menus, les sous-menus, les menus contextuels et les classes dérivées (`ItemMenuAtteignable`), activable et désactivable (comparaison).
  3. Un style implicite de `MenuItem` (ressources de l'application) qui pose le lien : ne s'applique pas aux classes dérivées (style choisi par type exact) ; désactivation moins simple.
  4. Peer dérivé qui redéfinit `GetAcceleratorKeyCore` : seulement pour une classe dérivée (`ItemMenuAtteignable`).
  5. Patch Harmony de `UIElementAutomationPeer.GetAcceleratorKeyCore` pour les `MenuItem` : le plus proche d'une correction de WPF, mais touche une méthode commune à tous les peers ; inutile ici.
- **Boutons liés à une commande** (constat de l'utilisateur, NVDA, .NET 10, 2026-11-17, bouton Gras de la barre de mise en forme) : NVDA dit « Gras Bascule non enfoncée Toggle bold ». Code de WPF (`ButtonBaseAutomationPeer.GetAcceleratorKeyCore`) : sans `AutomationProperties.AcceleratorKey`, un `ButtonBase` lié à une `RoutedUICommand` expose le **texte de la commande** (« Toggle bold », non traduit) comme raccourci ; NVDA le lit comme un raccourci. Les `MenuItem` n'ont pas ce repli (rien n'est exposé). De plus, les `EditingCommands` n'ont aucun raccourci dans `InputGestures` (ils sont posés comme raccourcis de classe de l'éditeur) : l'application ne peut pas les lire et doit les déclarer elle-même.
- **Double annonce confirmée** (utilisateur, NVDA, 2026-11-17) : avec `AcceleratorKey` « Ctrl+B » et l'infobulle « Gras (Ctrl+B) », NVDA dit « Gras, bascule, non enfoncée, Ctrl+B, Ctrl+B » : WPF expose l'infobulle comme `HelpText` (texte d'aide) quand aucun n'est posé. Correction retenue : `AutomationProperties.HelpText` d'une seule espace (non lue par NVDA, empêche le repli), infobulle complète conservée à l'écran.
- **Piège** : un gestionnaire de classe sur `Loaded` (`EventManager.RegisterClassHandler(typeof(MenuItem), LoadedEvent, …)`) n'est **jamais appelé** : WPF ne diffuse `Loaded` qu'aux éléments qui ont un gestionnaire propre (`BroadcastEventHelper`, drapeau `SubtreeHasLoadedChangeHandler`). Constaté avec NVDA (aucun raccourci annoncé). Utiliser des événements toujours levés : `MenuItem.SubmenuOpened`, `ContextMenu.Opened`, `Keyboard.PreviewGotKeyboardFocus`.
- Choix de l'utilisateur (2026-11-17) : moyen 2 (gestionnaire de classe pour tous les `MenuItem`), `Correctifs/CorrectifRaccourciMenu.cs`, item *Correctif > Annoncer les raccourcis des menus* (`Specs/Correctifs.md`).
- **Version Harmony** (choix de l'utilisateur, 2026-11-17, Harmony étant déjà là pour les lignes vides) : `Correctifs/CorrectifRaccourciMenu.cs` réécrit, deux postfix sur des méthodes protégées documentées (`UIElementAutomationPeer.GetAcceleratorKeyCore` pour les `MenuItem`, `ButtonBaseAutomationPeer.GetAcceleratorKeyCore` pour les boutons liés à une commande) ; plus aucune propriété modifiée. Vérifié hors application (programme console temporaire), identique en .NET 10.0.15 et 4.8 : item Ouvrir « » natif, « Ctrl+O » corrigé ; item dont l'application a posé `AcceleratorKey` : inchangé ; bouton lié à `ToggleBold` : « ToggleBold » natif, vide corrigé ; bouton lié à `Copy` : « Copier » natif (texte de commande traduit), « Ctrl+C » corrigé ; patch retiré : natif.
- Point à surveiller dans AccessTest : les boutons de la barre de mise en forme ont une infobulle « Gras (Ctrl+B) » **et** `AcceleratorKey` « Ctrl+B » ; NVDA les dit peut-être en double (l'infobulle sert de texte d'aide dans WPF quand `HelpText` est vide).
