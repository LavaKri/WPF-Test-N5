# Constats — Texte : lignes vides, RichTextBox, orthographe

Constats d'essai (UIA, lecteur d'écran) repris de `Docs/Notes.md`, section 5, sans changement de contenu. Retour à l'index : [`Notes.md`](../Notes.md).

## Ligne vide dans `TextBox` / `RichTextBox` : lecture de la ligne voisine

Constat de l'utilisateur (NVDA et Narrateur, `TextBox` multiligne) : sur une ligne vide, le lecteur ne dit pas « vide » mais lit la ligne du dessous (puis la relit en arrivant dessus). **Confirmé par l'utilisateur** : identique en .NET Framework 4.8 et dans le `RichTextBox`.

- **Bug WPF connu**, indépendant de notre code, côté framework : [dotnet/wpf#7190](https://github.com/dotnet/wpf/issues/7190) « Screen-reader reads lines twice in a TextBox / TextBlock / RichTextBox » (signalé depuis 2011 d'après le ticket). Touche aussi `RichTextBox` et `TextBlock`. Pas de contournement officiel.
- Cause indiquée dans le ticket : `TextRangeAdaptor.ExpandToEnclosingUnit(TextUnit.Line)` (fournisseur UIA `TextPattern`). Sur une ligne vide, début et fin de la plage sont mal gérés : la plage « ligne » déborde sur la ligne suivante.
- Correctif proposé : [dotnet/wpf#11509](https://github.com/dotnet/wpf/pull/11509), une garde dans `ExpandToEnclosingUnit` (`lineRange.Start.CompareTo(lineRange.End) == 0` : plage vide pour une ligne vide). **Ouvert, non fusionné** (en attente de relecture depuis mars 2026), donc absent de toute version publiée. Le ticket ne donne pas de version cible.
- Côté NVDA : [nvaccess/nvda#1412](https://github.com/nvaccess/nvda/issues/1412) (2011). Microsoft a refusé de corriger (ticket interne « Accessibility 248630 » fermé) : la correction « perturberait l'automatisation de nombreuses applications publiques ». Aucun contournement côté NVDA. La PR #11509 risque donc de ne jamais être fusionnée.
- Code fautif (dotnet/wpf, `TextRangeAdaptor.cs`, `internal class TextRangeAdaptor`) : méthode privée `ExpandToEnclosingUnit(TextUnit unit, bool expandStart, bool expandEnd)`, cas `TextUnit.Line`. `lineRange` est un `TextSegment` (interne) obtenu par `textView.GetLineRange(_start)` ; sur une ligne vide, `lineRange.Contains(_end)` est faux, donc `_end` est ensuite étendu à la fin de la ligne **suivante**. La PR remplace la condition par `lineRange.Contains(_end) || lineRange.Start.CompareTo(lineRange.End) == 0`.
- Contrôles tiers : rien de publié. Telerik `RadRichTextBox` a des problèmes de lecture signalés ; l'éditeur riche DevExpress n'expose pas UIA dans ses documents ; AvalonEdit a un fournisseur `TextPattern` à lui, non évalué.
- Même symptôme dans d'autres frameworks (Qt, etc.) : ce n'est pas propre à WPF.
- **Non vérifié** : le test UIA direct (plages `Line` sur un texte `a / vide / b`) n'a pas été fait.
- Pistes de contournement :
  0. **Retenue et faite** (menu Correctif, `CorrectifLigneVide.cs`). Le transpiler trouve sa cible en .NET 10.0.15 et en .NET Framework 4.8.10008.0 : même structure de code interne. Effet sur la lecture confirmé par l'utilisateur (.NET 10) ; non testé en 4.8 avec un lecteur d'écran. **Patch à l'exécution avec [Harmony](https://www.nuget.org/packages/Lib.Harmony)** (`Lib.Harmony` 2.4.3, cibles `net48` et `net10.0`) : un *transpiler* sur la méthode privée ci-dessus ajoute la condition de la PR, en IL, juste après l'appel à `TextSegment.Contains`. Une quinzaine de lignes, appliquées une fois au démarrage. Corrige `TextBox` et `RichTextBox` d'un coup, pour NVDA comme pour Narrateur. Risques : dépendance externe, patch lié au code interne de WPF (à revérifier à chaque version), identité du code en 4.8 **non vérifiée**.
  1. `TextBox` dérivé + `AutomationPeer` dérivé de `TextBoxAutomationPeer` qui enveloppe le `ITextProvider` natif et renvoie, pour une ligne vide, une plage vide. Il faut envelopper aussi `ITextRangeProvider` (`Clone`, `Compare`, `Move*`…). Même code pour .NET 10 et 4.8, sans Nullable ni syntaxe réservée.
  2. Attendre la fusion de #11509 (aucune date).
  3. Ne rien corriger et documenter le défaut dans les résultats de test (c'est aussi l'objet de l'application de test).

## `RichTextBox` : texte illisible avec NVDA

Constat de l'utilisateur (2026-11-13, .NET 10) : dans l'onglet RichText, NVDA lit les lettres tapées, mais le texte ne peut pas être relu (flèches), y compris après chargement d'un fichier. Même résultat avec et sans le patch des lignes vides : **le patch n'est pas en cause**. Le `TextBox` fonctionne.

- Constat de code ([RichTextBoxAutomationPeer](https://source.dot.net/PresentationFramework/System/Windows/Automation/Peers/RichTextBoxAutomationPeer.cs.html)) : type de contrôle UIA `Document` (et non `Edit` comme le `TextBox`), motifs `Text` et `Scroll`.
- **Hypothèse, non vérifiée** : NVDA traite un `Document` en mode navigation, ce qui empêche la lecture normale au curseur. Les recherches faites n'ont pas confirmé ce point pour WPF.
- À tester : mode navigation ou mode focus (NVDA+Espace), Narrateur, relevé UIA du `RichTextBox`.
- **Mise à jour** : l'hypothèse « mode navigation » est écartée. Copies de test (`_diag`) : sans le nom accessible **ou** sans la mise à jour de position à chaque `SelectionChanged`, saisie et relecture fonctionnent. Cause du chargement illisible : `Charger` remplaçait `RtbEditeur.Document` alors que le peer UIA reste lié au document d'origine ; corrigé dans `Net10` (on vide et remplit le document existant). Utilisateur : saisie et chargement OK dans les deux copies.
- Le patch des lignes vides, dans sa première version (condition de la PR seule), **n'agissait pas** dans le `RichTextBox` (constat de l'utilisateur). La PR #11509 affirme couvrir le `RichTextBox` (« TextDocumentView renvoie un segment vide pour un paragraphe vide »), mais n'a été testée avec NVDA que sur un `TextBox`.
- Projet qui a résolu le cas dans un `RichTextBox` WPF : [coryj627/slate](https://github.com/coryj627/slate), PR [#1868](https://github.com/coryj627/slate/pull/1868) (issue [#1687](https://github.com/coryj627/slate/issues/1687), novembre 2026). Technique : enveloppe du motif `Text`, avec une `ExpandToEnclosingUnit` réécrite pour un curseur (plage vide) : on part du **début** de la ligne du curseur, la fin s'arrête au début de la ligne suivante ou à la fin du paragraphe. Constat cité : « l'extension de WPF ne se trompe que depuis la fin d'une ligne ». Testé avec NVDA. **Licence AGPL v3** : s'inspirer de l'idée, ne pas copier le code (sinon l'application passerait sous AGPL).
- **Journal UIA** (copie `DiagC`, NVDA, patch actif, texte `un / vide / trois`) : NVDA n'appelle que `ExpandToEnclosingUnit(Line)` (plus `MoveEndpointByUnit(End, Character, 1)` et `ExpandToEnclosingUnit(Character)`). `TextBox` : la ligne vide donne `[]`, le patch agit. `RichTextBox` : la ligne vide donne `[\r\ntrois]` ; la plage de ligne d'un paragraphe vide n'est pas vide, la condition de la PR ne se déclenche pas.
- Correctif élargi (`CorrectifLigneVide.cs`) : pendant un appel public `ExpandToEnclosingUnit(Line)` (préfixe Harmony qui lève un drapeau, *finalizer* qui le baisse), la condition est toujours vraie : la fin est ramenée à la fin de la ligne du début. Vérifié applicable en .NET 10.0.15 et 4.8.10008.0. **Confirmé par l'utilisateur avec NVDA** pour `TextBox` et `RichTextBox` (.NET 10).
- Point resté inexpliqué : dans la première copie de test, la saisie redevenait lisible sans le nom accessible ou sans la mise à jour de position ; mais la copie `DiagC` (qui a les deux, plus le correctif du chargement) fonctionne. Cause la plus probable : le document remplacé par un chargement antérieur dans la même session. Non démontré.
- Observation sur le code WPF : `ITextRangeProvider.ExpandToEnclosingUnit` public ramène toujours `_end` à la position d'insertion qui suit `_start` avant d'appeler la méthode privée ; pour l'unité `Line`, le bon résultat est donc toujours la ligne qui contient `_start`.

## Document mis en forme dans un `RichTextBox` : seul le tableau est signalé

Constat de l'utilisateur (NVDA, .NET 10, 2026-11-17, onglet RichText, *Charger > Document mis en forme*) : NVDA ne signale que le tableau ; titre, listes et lien ne sont pas annoncés comme tels ; Ctrl+Alt+flèches ne fonctionne pas dans le tableau. Recherches du 2026-11-17, dans le code de WPF (`TextRangeAdaptor.cs`, peers de `System/Windows/Automation/Peers`) et de NVDA (`NVDAObjects/UIA/__init__.py`, `NVDAObjects/UIA/wordDocument.py`, `documentBase.py`) :

| Élément | Ce que WPF expose (UIA) | Ce que NVDA attend | Conséquence |
|---|---|---|---|
| Titre (`Paragraph` en grand et gras) | Rien : aucun peer pour `Paragraph` ; la plage de texte n'expose pas l'attribut `StyleId` (absent de la table d'attributs de `TextRangeAdaptor`) | Attribut de texte `StyleId` compris entre `StyleId_Heading1` et `StyleId_Heading9` (`_getFormatFieldHeadings`) | Pas de titre. Un `FlowDocument` n'a d'ailleurs pas de notion de titre : c'est une mise en forme. |
| Listes (`List`, `ListItem`) | Aucun peer pour `List` ni `ListItem` ; seulement l'attribut `BulletStyle` (puce ou numéro, tiré de `MarkerStyle`) | Des éléments UIA de type `List` / `ListItem` ; NVDA n'utilise pas `BulletStyle` | Pas de liste annoncée. |
| Lien (`Hyperlink`) | Un élément enfant de type `Hyperlink` (`HyperlinkAutomationPeer`, motif `Invoke`), dans la vue « contrôle » seulement s'il est visible ; pas d'attribut de texte `Link` | Surtout l'attribut de texte `Link` (`_getFormatFieldLinks`, `UIA_LinkAttributeId`) ; les éléments enfants sont aussi parcourus (`getChildren`), mais le lien n'est pas annoncé dans ce cas (constat) | Pas de lien annoncé. |
| Tableau (`Table`) | Élément de type `Table`, motif `Grid` seulement (pas `Table` : ni en-têtes de ligne ni de colonne) | Rôle tableau, nombre de lignes et de colonnes | **Signalé** (seul élément reconnu). |
| Cellule (`TableCell`) | Type **`Custom`** (nom de type « cell »), motif `GridItem` seulement | Rôle cellule (`TABLECELL`, `DATAITEM`, en-têtes) pour lire ligne, colonne et en-têtes (`_getControlFieldForUIAObject`) | Cellules non reconnues : ni position ni en-tête. |
| Navigation de tableau (Ctrl+Alt+flèches) | — | Commandes fournies par `DocumentWithTableNavigation`, dont héritent seulement le mode navigation et le document Word en UIA (`WordDocument(UIADocumentWithTableNavigation, …)`) | **Indisponible** dans une zone d'édition UIA ordinaire comme le `RichTextBox`, quoi que fasse WPF : limite de NVDA. |

Correctif global choisi par l'utilisateur (2026-11-17) : `Correctifs/CorrectifLectureRiche.cs`, par étapes. **Étape 1 faite (titres et liens)** : préfixe Harmony de `TextRangeAdaptor.ITextRangeProvider.GetAttributeValue` pour les identifiants 40034 (`StyleId`) et 40035 (`Link`) ; titres marqués par la propriété attachée `NiveauTitre` ; pour un lien, la plage elle-même, enveloppée par `TextRangeProviderWrapper.WrapArgument` (WPF note dans son code qu'une valeur d'attribut de type plage doit être enveloppée). Vérifié hors application (programme console temporaire, appels directs du motif `Text`), identique en .NET 10.0.15 et 4.8 : natif « non pris en charge » partout ; corrigé : titre 70001, texte ordinaire 70012, document entier « mélangé » ; lien entier, mot du lien et curseur dans le lien : une plage ; hors lien « non pris en charge » ; à cheval « mélangé » ; retiré : natif. Non vérifié : le passage de la plage par UIA jusqu'à NVDA (hors processus).

**Étape 2 faite (cellules, 2026-11-18)** : postfix de `TableCellAutomationPeer.GetAutomationControlTypeCore` (`DataItem`), de `TableCellAutomationPeer.GetPattern` (motif `TableItem` ajouté, en-tête de colonne = cellule de même colonne de la première ligne d'un tableau marqué `LigneEntete`) et de `ContentElementAutomationPeer.GetNameCore` (nom des cellules d'en-tête = leur texte, car NVDA lit l'en-tête par ce nom : `_getTextFromHeaderElement`). Vérifié hors application, identique en .NET 10.0.15 et 4.8 : natif `Custom`, sans motif `TableItem`, noms vides ; corrigé : `DataItem`, ligne 1 colonne 2 (base 0), 1 en-tête de colonne, en-tête nommé « Prix », cellules ordinaires sans nom ; retiré : natif. Hors fenêtre, WPF ne fabrique pas le fournisseur UIA de l'en-tête (`ProviderFromPeer` rend null sans fenêtre) : la lecture de l'en-tête par NVDA reste à vérifier dans l'application.

**« Non disponible »** (constat de l'utilisateur, NVDA, 2026-11-18) : « Tableau non disponible de 4 lignes et 3 colonnes », « Ligne 2 non disponible ». Cause, code de WPF : `FlowDocument.IsEnabledCore` rend `RichTextBox.IsDocumentEnabled` ; faux par défaut, il désactive tout le contenu du document, et `ContentElementAutomationPeer.IsEnabledCore` transmet `IsEnabled` à UIA. Correction : postfix de `ContentElementAutomationPeer.IsEnabledCore`, vrai pour `Table` et `TableCell`, liens inchangés. Vérifié hors application (.NET 10 et 4.8, `IsDocumentEnabled` faux) : natif tableau, cellule et lien désactivés ; corrigé tableau et cellule activés, lien désactivé ; retiré : natif.

**Lien et clavier** (constat de l'utilisateur, NVDA, 2026-11-18) : *Activer les liens* coché (`IsDocumentEnabled`), le lien n'est plus « indisponible », mais il n'est **pas activable au clavier** : sur le lien, les touches écrivent dans le texte, et Entrée ne fait rien (ni activation, ni saut de paragraphe). Activation seulement à la souris, ou par un client UIA qui appelle `Invoke` (`HyperlinkAutomationPeer`). Suite (2026-11-18, demande de l'utilisateur) : l'onglet RichText active le lien sous le curseur par Entrée, en appelant ce même `Invoke` (`Specs/RichText.md`, 2c) ; l'item s'appelle désormais *Document interactif*.

**Comportement attendu des touches dans un tableau d'éditeur** (référence : Word, car le `RichTextBox` est une zone d'édition, pas une grille de données) : Gauche / Droite caractère par caractère, en passant à la cellule suivante en fin de cellule ; Haut / Bas ligne au-dessus ou au-dessous dans la même colonne (constaté dans WPF) ; Début / Fin dans la cellule ; Ctrl+Début / Ctrl+Fin dans le document ; Tab / Maj+Tab cellule suivante / précédente (Word ajoute une ligne après la dernière cellule ; dans WPF, Tab quitte l'éditeur tant que *Tab insère une tabulation* est décoché, le comportement coché n'est pas vérifié) ; Entrée nouveau paragraphe dans la cellule ; les lettres écrivent dans la cellule (constaté). NVDA annonce « ligne X » en changeant de ligne (constaté), « colonne Y » et l'en-tête en changeant de colonne (à confirmer). Ctrl+Alt+flèches : indisponible (limite de NVDA).

**Étape 3 faite (listes, 2026-11-18).** Recherches, code de WPF : tous les chemins du motif `Text` (`TextContainerHelper.GetEnclosingAutomationPeer`, `GetAutomationPeersFromRange`, `IsImmediateAutomationChild`) obtiennent le peer d'un élément par `ContentElementAutomationPeer.CreatePeerForElement`, donc `ContentElement.CreateAutomationPeer`, qui appelle `OnCreateAutomationPeer` (virtuelle, `null` dans `ContentElement`, redéfinie ni par `TextElement`, ni `Block`, ni `List`, ni `ListItem`) et garde le résultat en cache (`AutomationPeerField`, drapeau `HasAutomationPeer`) ; `TextAdaptor.RangeFromChild` accepte tout `TextElement`. Code de NVDA : une liste dans un texte est un élément englobant de rôle `LIST` ; `ControlField.getPresentationCategory` en fait un conteneur (« liste » / « hors liste », réglage *Listes* respecté) seulement avec l'état `READONLY`, sinon une ligne unique (zone de liste) ; un élément de liste (`LISTITEM`) n'est annoncé qu'avec plus de détails (`extraDetail`). L'état `READONLY` d'un élément UIA vient de `ValueIsReadOnly` (motif `Value`) ou, à défaut, de l'attribut `IsReadOnly` de son propre motif `Text` (`_getReadOnlyState`). Pour Word en UIA (`NVDAObjects/UIA/wordDocument.py`), NVDA ajoute lui-même `READONLY` aux listes, puis leur donne le rôle « texte modifiable » pour ne pas les annoncer (compatibilité avec l'ancienne prise en charge de Word) ; il y lit la puce ou le numéro, que Word met dans le texte, comme préfixe de ligne (`line-prefix`, [nvda#7971](https://github.com/nvaccess/nvda/issues/7971)). Recherche extérieure : aucune solution publiée pour les listes d'un `RichTextBox` WPF.

Correctif : postfix de `ContentElement.OnCreateAutomationPeer` (un peer dérivé de `TextElementAutomationPeer` pour `List` et `ListItem`, types `List` et `ListItem`, la liste avec un motif `Value` en lecture seule) ; cache de WPF effacé au retrait du correctif. Vérifié hors application (programme console temporaire, identique en .NET 10.0.15 et 4.8, `IsDocumentEnabled` faux) : natif, aucun peer de liste, élément englobant d'un mot de la liste = le document ; corrigé, liste `List` activée, motif `Value` en lecture seule, 3 enfants `ListItem` activés, englobant = `ListItem`, hors liste = le document ; retiré : natif ; réactivé : corrigé. Non vérifié : ce que NVDA en annonce. Solutions écartées (2026-11-18, choix de l'utilisateur) : module NVDA pour AccessTest (lecture de `BulletStyle`, numéros calculés), nom des éléments de liste égal à leur puce ou numéro lu par ce module, puces écrites dans le texte.

Corrections possibles pour la suite (non faites) :

- **Titres et liens** : patch Harmony de `TextRangeAdaptor.GetAttributeValue` (implémentation de `ITextRangeProvider`) : répondre à `UIA_StyleIdAttributeId` (40034) pour un paragraphe marqué comme titre par l'application (propriété attachée, niveau 1 à 9), et à `UIA_LinkAttributeId` (40035) quand la plage est dans un `Hyperlink`. Les identifiants sont des entiers UIA : WPF ne connaît pas ces attributs, il faut les intercepter avant sa recherche dans sa table.
- **Cellules** : patch de `TableCellAutomationPeer` (type `DataItem`, et motif `TableItem` avec l'en-tête de colonne) : NVDA annoncerait la position et l'en-tête en entrant dans une cellule. La navigation Ctrl+Alt+flèches resterait indisponible.
- **Navigation de tableau** : seulement côté NVDA (module d'application NVDA pour AccessTest, en Python, qui ajoute `DocumentWithTableNavigation` à la zone d'édition) : hors de WPF.

## Suggestions d'orthographe dans un menu contextuel personnalisé

Lu dans le code source de WPF (dotnet/wpf, `TextEditorSpelling.cs`, `TextEditorContextMenu.cs`, `TextBox.cs`), 2026-11-16 :

- Le menu natif et les commandes `EditingCommands.CorrectSpellingError` / `IgnoreSpellingError` (exécution et `CanExecute`) trouvent la faute par `TextEditor.GetSpellingErrorAtSelection`, **interne**. Règle : sans sélection, le caractère du côté de la `LogicalDirection` du curseur, ou l'autre côté s'il n'y a rien ou un blanc ; avec sélection, le premier caractère non blanc de la sélection.
- `TextBox.GetSpellingError(i)` (public) renvoie la faute qui contient le caractère `i` (essai vers l'avant depuis `i`, puis vers l'arrière depuis `i + 1`). L'exemple de Microsoft (`GetSpellingError(CaretIndex)` pour remplir le menu, puis les commandes pour corriger) applique donc deux règles différentes : par exemple, curseur à la fin d'un mot (après F7), `GetSpellingError` regarde le blanc qui suit et ne trouve rien, alors que la commande trouverait le mot.
- Au clic droit hors de la sélection, le gestionnaire de classe `OnContextMenuOpening` place le curseur sous la souris **avant** les gestionnaires de l'application, même quand le contrôle a un `ContextMenu` personnalisé (pas au clavier : `CursorLeft == -1`).
- Choix d'AccessTest : appeler `GetSpellingErrorAtSelection` par réflexion (`TextEditor._GetTextEditor(contrôle)`), pour avoir exactement la détection du menu natif. Fragile si WPF change ce nom interne (vérifier en .NET Framework 4.8).
- Essai abandonné (2026-11-16) : chercher la faute à plusieurs positions autour du curseur et corriger par `SpellingError.Correct` / `IgnoreAll`. Les positions voisines pouvaient tomber sur le mot d'à côté ; retiré à la demande de l'utilisateur au profit de la détection de WPF.

## Réutiliser le correctif des lignes vides dans un autre projet

État actuel : fichier autonome `Correctifs/CorrectifLigneVide.cs` (espace de noms `CorrectifsWpf`), à copier ou à inclure par lien. Il exige Harmony. Vérifié dans un projet vierge : compile sans `using` implicites, en C# 7.3 pour `net48`, et le patch s'applique et se retire en .NET 10.0.15 et en .NET Framework 4.8.10008.0.

Harmony : licence **MIT** (copie, modification, redistribution permises, en gardant la mention de copyright et la licence). Embarque MonoMod.Core, qui fait le détour des méthodes en mémoire. Technique : Harmony fabrique en mémoire une copie modifiée de la méthode (IL d'origine + préfixe, *finalizer*, *transpiler*), la fait compiler par le JIT, puis écrit au début du code machine d'origine un saut vers cette copie. Ce n'est **pas** une méthode d'extension (simple facilité du compilateur, qui ne change pas une méthode existante). Recopier Harmony serait légal mais difficile : code machine par processeur, recompilation par paliers du JIT, écarts entre .NET Framework et .NET. À éviter.

**Idées à étudier** (rien n'est fait) :
1. **Bibliothèque partagée** `CorrectifsWpf` (projet DLL ciblant `net48` et `net10.0-windows`) qui contient le correctif et référence le paquet `Lib.Harmony`. Les applications la référencent (`ProjectReference`, ou paquet NuGet plus tard) et reçoivent Harmony automatiquement. Avantage : une seule copie du code, versionnée ; pratique si d'autres correctifs WPF s'ajoutent.
2. **Joindre la DLL de Harmony** (`0Harmony.dll`, présente dans le paquet et copiée dans le dossier de sortie) au lieu de passer par NuGet : la référencer directement et livrer son fichier `LICENSE` (MIT) avec. Utile pour un projet sans accès à NuGet ou au format `.csproj` ancien.
3. Les deux se combinent : bibliothèque partagée + `0Harmony.dll` jointe.

Points à garder dans tous les cas : retester le patch à chaque version majeure de .NET (il dépend du code interne de WPF) ; `Activer()` lève une exception si la cible a changé, l'appelant doit la capturer.
